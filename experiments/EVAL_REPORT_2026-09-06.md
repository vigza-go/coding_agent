# 分层时序摘要与滚动摘要对照实验报告

## 1. 实验结论

本次实验使用同一批 5 道 LongMemEval 原文题目，在 16K、32K、64K 三种上下文预算下，分别运行分层时序摘要（`hier`）和传统滚动摘要（`roll`）。历史消息全部使用原文完整输入，没有截断，也没有拼接不同题目。

结论如下：

1. 16K 预算下，当前分层算法 5 道题全部因压缩区无法继续合并而失败；滚动摘要 5 道题全部完成。
2. 32K 预算下，分层算法平均调用 93.8 次，滚动摘要平均调用 8.2 次；分层输入 token 多约 51%。
3. 64K 预算下，分层算法平均调用 17 次，滚动摘要平均调用 4.2 次；分层输入 token 反而少约 8%，但调用次数仍约为滚动摘要的 4 倍，输出 token 略高。
4. 分层算法目前不能被评价为“更省 token”。它的主要价值是保留时间层次：旧信息逐层晋级，近信息保持更细粒度。
5. 本实验只测了摘要成本，没有测摘要后的回答质量，因此不能据此证明分层摘要的语义保留能力更强。

### 4.2 失败原因

5 道题的分层算法都触发了同一种异常：

```text
CompressionInvariantError:
compression region exceeds its limit but has no adjacent same-level pair
```

出现过的层级序列包括：

```text
[L5, L3]
[L5, L4, L3, L2]
[L5, L3, L0]
[L5, L4, L2]
```

这说明当前压缩区已经超过 4K，但按照“只合并相邻同层块”的规则，已经找不到合法的下一次合并。这个问题是当前分层算法在小压缩区下的稳定性边界，不是模型请求失败。

因此 16K 档不能用于比较两种算法的完整 token 成本；它应当记录为：

```text
hier：5/5 失败
roll：5/5 完成
```

## 7. 对算法的评价

### 7.1 分层算法已经验证的部分

分层算法的核心时间结构在 32K 和 64K 下正常工作：

```text
原始消息 → L0 → L1 → L2 → ...
```

32K 测试最高达到 L4，64K 测试达到 L0～L1。这与预算大小一致：预算越小，压缩触发越早，层级晋升越多。

这说明“越早的信息压缩次数越多、越近的信息保留得更清晰”的设计方向是成立的。

### 7.2 当前算法的代价

分层算法每次触发时要先生成多个 L0，然后再进行逐级合并；滚动算法每次只需要把旧摘要和新前缀重新摘要成一个块。因此：

```text
分层：多个局部摘要 + 多次父块合并
滚动：一次整体重摘要
```

这使得分层算法在 32K 下明显更贵，在 64K 下虽然输入 token 略少，但调用次数仍然更多。

### 7.3 当前最重要的问题

16K 下的失败表明，当前合并规则并不能保证压缩区最终一定满足预算：

```text
压缩区超限
且没有相邻同层块
```

如果项目需要支持 16K 上下文，必须为这种情况增加处理策略，否则分层上下文会在长对话中中断。

## 8. 评测口径限制

本报告中的 token 是评测程序用 `estimate_tokens()` 对摘要器 transcript 和输出做的本地估算，不是供应商 API 返回的真实 `usage_metadata`。它没有直接统计：

- 摘要系统提示词和消息包装开销；
- provider 的真实 tokenizer 差异；
- `cache_read` 和 `cache_creation`；
- 请求失败但已经产生的费用。

`calls` 包含 `RetryingSummarizer` 的每次尝试，因此包括因超限或内容校验而产生的重试调用。

此外，当前滚动对照实现跳过了分层合并步骤，没有把单个滚动块严格限制在压缩区上限内。因此 32K/64K 的结果可以用于观察趋势，但还不应解释为最终的严格成本证明。

最后，`press_max` 是数据库中所有 active memory block 的范围重叠统计，不等于当前真正送入模型的块数量。本报告没有使用它作为结论依据。

## 10. 建议的后续工作

1. 先修复 16K 下的无可合并块问题，再决定是否将 16K 纳入正式对照。
2. 给评测结果增加选中 block 的 level、消息范围和 `token_count`，直接检查块大小是否符合预期。
3. 让滚动摘要也严格受同一个压缩区预算约束。
4. 后续如果要评价“分层是否更好”，需要在成本实验之外增加回答质量实验；当前数据集中的答案字段可以用于质量评测，但不应参与本次成本样本筛选。
